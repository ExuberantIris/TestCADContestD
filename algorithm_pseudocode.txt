第一部分　問題背景與核心概念
================================================================================

1.1　時鐘樹的結構
--------------------------------------------------------------------------------
把整個晶片的時鐘分配網路想成一棵樹：

    ROOT（時鐘來源）
     │
    buffer（時鐘緩衝器：把訊號放大、順便產生一段延遲，再往下傳）
     │   ╲
    buffer  FF（flip-flop：樹的葉節點，真正使用時鐘訊號做事的暫存器）
     │
    FF

每顆 buffer 都是某個 cell library 裡某一種「cell」的實例。每種 cell 固定了：

  - 面積（width × height）
  - 在某個 fanout（這顆 buffer 驅動幾個 child）下的延遲時間

時鐘訊號從 ROOT 往下傳，每經過一顆 buffer 就累加它的延遲。所以每個 FF 收到時鐘訊號
的時間點，等於「ROOT 到這個 FF 路徑上所有 buffer 延遲的總和」，程式裡稱為這個 FF 的
「累積時鐘延遲」（d_clk_ss / d_clk_ff，差別見下一節）。


1.2　Setup / Hold，SS / FF corner
--------------------------------------------------------------------------------
一條「path」是「某個 FF 送資料出去（launch）→ 另一個 FF 收資料（capture）」的一段
資料路徑。同一條 path 同時要過兩種時序檢查：

  Setup check：資料必須在下一個時鐘邊緣*之前*穩定下來，否則 capture 端會收錯資料。
               這個檢查假設電路跑在「最慢」的情況下（SS corner，slow-slow）。

  Hold check：資料不能變動得太快，否則同一個時鐘邊緣會把下一筆資料也一起抓進去。
              這個檢查假設電路跑在「最快」的情況下（FF corner，fast-fast）。

正因為同一顆 buffer 在「最慢」跟「最快」的物理條件下延遲不一樣，library 裡每顆 cell
都各自列了一張 SS_DELAY 表跟一張 FF_DELAY 表（依 fanout 查表），同一顆 buffer 在程式
裡永遠同時帶著兩個延遲數值，setup 相關計算用 SS 那組，hold 相關計算用 FF 那組。


1.3　Slack、WNS、TNS
--------------------------------------------------------------------------------
slack（餘裕）是「還剩多少安全邊際」，沒違規是正的，違規是負的：

    skew_ss        = capture 的 d_clk_ss − launch 的 d_clk_ss
    slack_setup_ss = clock_period − t_setup − data_ss + skew_ss

    skew_ff        = capture 的 d_clk_ff − launch 的 d_clk_ff
    slack_hold_ff  = data_ff − t_hold − skew_ff

  WNS（Worst Negative Slack）= 所有 path 裡面最差（最負）的 slack
  TNS（Total Negative Slack）= 所有違規（slack < 0）path 的 slack 加總（恆 ≤ 0）


1.4　Useful Skew：這個題目真正要解的東西
--------------------------------------------------------------------------------
看 setup slack 的公式：想讓它變大，要讓 skew_ss 變大，也就是讓「capture 端的時鐘故意
晚一點到」。這個「故意讓兩端時鐘不同步」的手法叫 useful skew —— 題目要我們做的不是把
所有 FF 的時鐘對齊，而是故意調出剛好對的「不對齊」程度，去把 timing violation 解掉。


1.5　我們唯二能做的兩種操作
--------------------------------------------------------------------------------
  (1) Resize — 把某顆既有 buffer 換成 library 裡別的 cell（不同面積、不同延遲）
  (2) Insert — 在某條既有的 parent→child 邊上，插入一顆新 buffer
               （命名規則固定：NEW_BUF_0、NEW_BUF_1、...，往下遞增）

硬性限制：
  - 不能刪除或改名既有元件，不能改變既有元件之間的祖先/子孫關係
  - 元件 pin 不能空接；FF 只能被單一顆 buffer 驅動
  - buffer 的 fanout 不能超過它所屬 cell 的 max_fanout
  - 單筆測資（含讀檔、計算、寫檔）總執行時間不能超過 600 秒，超時視同 0 分


1.6　評分公式
--------------------------------------------------------------------------------
    Score = α[(1 − TNS_SS/TNS_SS_ori) + (1 − WNS_SS/WNS_SS_ori)]
          + β[(1 − TNS_FF/TNS_FF_ori) + (1 − WNS_FF/WNS_FF_ori)]
          + γ(1 − Area/Area_ori)

    α = 0.6（setup，權重最高）　β = 0.2（hold）　γ = 0.2（面積）

"_ori" 代表完全沒被我們動過的原始設計的數值，是固定不變的分母，整個最佳化過程中
分數的改善，全部是相對於這個原始基準算出來的。

第二部分　演算法總覽
================================================================================

2.1　核心資料抽象：Branch　（→ include/lp_types.hpp, src/lp_branch.cpp）
--------------------------------------------------------------------------------
演算法不是直接操作「樹的節點」，而是操作「branch」——樹上每一條 parent→child 邊。
每條邊依 child 的種類分兩類：

  ExistingBuf　child 是一顆既有 buffer（含我們自己插入的 NEW_BUF_X）。
               這條邊「可以 resize」。每條 branch 記錄：

                 fanout        child 自己驅動幾個下一層節點
                 d_ss_min/max  在這個 fanout 下，library 所有 cell 能達到的
                               SS 延遲最小值／最大值
                 d_ff_min/max  同上，hold corner
                 allow_zero_cell   這條邊的 child 是不是我們自己插入的
                                   NEW_BUF_*（細節見 4.7 節）

  Insertable　 child 直接是一顆 FF，中間沒有任何 buffer。這是比較早期版本的分類，
               目前真正的插入決策已經改用 4.3 節的獨立搜尋邏輯，這個分類在目前的
               pipeline 裡 delay 永遠釘在 0，不影響任何資源分配決策，保留只是為了
               讓底層的限制圖（3.2 節）formula 維持一致。

bounds（d_ss_min/max、d_ff_min/max）的計算規則：
    對 library 裡每一顆 cell c：
        若 c 是 zero cell 且這條 branch 的 allow_zero_cell 是 false → 跳過
        否則：用 c 在這個 fanout 下的延遲，更新 min/max
這保證了「只有插入的新 buffer 才看得到 0 延遲這個選項，既有的 buffer 永遠看不到」。


2.2　整體流程
--------------------------------------------------------------------------------
這裡要特別說清楚一件容易被忽略的事：**同一個 LP Init 演算法，整條 pipeline 裡
總共被呼叫兩次**，第一次是在 Phase 0 用來「診斷」哪裡需要插入，第二次才是真正
餵給 Greedy 的起跑點。

    讀檔（兩份：design 拿來改，orig_design 永遠不動，當最終比較基準）
        │
        ▼
    建立初始 Branch 模型
        │
        ▼
    Phase 0　找出該插入 buffer 的位置　［第 4 節］
        (a) 第一次呼叫 LP Init（第 3 節的演算法）
            　→ 算出「完全不插入、只靠 resize」數學上能做到的最佳解
        (b) 看這個解之下，哪些 path 仍然違規，依此決定插入候選位置
        (c) 插入新 buffer，並安裝 zero cell 安全閥（讓插入可以被整顆撤銷）
        (d) 拓樸變了，重建 Branch 模型 —— 現在新插入的 buffer 也是
            ExistingBuf branch 的一種，且它的 bounds 含 0 這個選項
        │
        ▼
    Phase 1　套用 LP Init 的解　［第 5 節］
        (a) 第二次呼叫 LP Init —— 跟 (a) 用的是完全相同的演算法（第 3 節），
            差別只是這次的 Branch 模型已經包含插入的 buffer
        (b) 把這次解出來的連續延遲值，吸附到 library 裡最接近的真實 cell
        │
        ▼
    Phase 2　Greedy 區域搜尋：反覆嘗試「換哪顆 buffer 的 cell 能讓分數變好」　［第 6 節］
        │   （跑兩次：一次從 Phase 1 的解開始，一次從原始設計開始，取分數較高者）
        ▼
    Phase 3　套用最終解 → 清掉縮到 0 的插入 buffer → 合法性檢查 → 寫出結果檔　［第 7 節］

每個階段都對應一個 src/main.cpp 裡的區塊；後面的章節會逐一展開。時間預算如何在
這些步驟之間分配、以及讀檔/搜尋過程裡用了哪些加速技巧，獨立整理在第八部分。



================================================================================
第三部分　LP Init 演算法 — resize-only 的精確解
================================================================================
→ src/lp_mo_init.cpp

這個演算法回答的問題是：「如果完全不插入新 buffer，只靠調整既有 buffer 的大小，
數學上最好能把 WNS 改善到多少？」整條 pipeline 裡，這個演算法被呼叫兩次（一次在
Phase 0 當診斷工具、一次在 Phase 1 當 Greedy 的起跑點，見 2.2 節），但**演算法
本身完全一樣**，這裡先把機制講清楚，後面提到的時候只會說「呼叫第 3 節的演算法」。

這不是一般人想的「丟給某個現成的 LP solver」，是針對「樹形差分限制系統」設計的
精確演算法，SS、FF 兩個 corner 各自獨立跑一次，邏輯相同。


3.1　核心變數：psi（相對偏移量）
--------------------------------------------------------------------------------
對每個節點定義：

    psi(node) = 這個節點的累積時鐘延遲，相對於「目前（還沒優化前）的數值」，
                偏移了多少

一開始所有節點 psi = 0。之所以用「相對偏移」而不是直接算絕對延遲，是因為這樣
沒被任何違規逼著動的分支，會自然停在 psi=0（也就是維持原狀），不會被迫飄到某個
極端值去——只有真正被限制逼著移動的節點，psi 才會偏離 0。


3.2　建圖：兩種有向邊
--------------------------------------------------------------------------------
先約定一個讀法：一條 u→v、權重 w 的有向邊，代表限制「psi(v) ≤ psi(u) + w」。
下面兩種邊，都是把一條物理限制改寫成這個形式。

(a) Box edge —— 每條 ExistingBuf branch 自己的範圍限制 [lo, hi]（與目標 tau
    無關，固定不變）。設這條 branch 目前延遲是 orig，新延遲必須滿足：

        lo ≤ orig + psi(child) − psi(parent) ≤ hi

    拆成兩個方向的不等式，整理成「psi(v) ≤ psi(u) + w」的形式：

        psi(child) − psi(parent) ≤ hi − orig　⟹　parent → child，權重 = hi−orig
        psi(parent) − psi(child) ≤ orig − lo　⟹　child → parent，權重 = orig−lo

(b) Cross edge —— 每條 path 的 timing 限制，這個推導比較關鍵，完整拆解如下。
    以 setup 為例，假設這條 path 在「psi 全部還是 0」時的目前 slack 是 base：

        新的 slack(p) = base + psi(capture) − psi(launch)
        　　（因為 capture、launch 的累積延遲各自加上了 psi(capture)、psi(launch)，
        　　　而 slack 公式裡的 skew_ss 正好是兩者相減）

    我們想知道：要求新 slack 至少要有 tau，這個限制改寫成 psi 的不等式：

        base + psi(capture) − psi(launch) ≥ tau
        ⟹  psi(launch) − psi(capture) ≤ base − tau
        ⟹  psi(launch) ≤ psi(capture) + (base − tau)

    對照「psi(v) ≤ psi(u) + w」的形式，這正是一條 **capture → launch，
    權重 = base − tau** 的邊。hold 的限制方向相反，推導完全對稱，結果是
    **launch → capture，權重 = base − tau**。

    這條邊的意思現在很直接：tau 設得越嚴格（越要求 slack 不能太差），
    base − tau 這個權重就越小，代表 psi(launch) 被壓得更低（或 psi(capture)
    要更高才能補回來）——也就是要求 capture 端的時鐘要更明顯地晚於 launch 端，
    剛好對應 1.4 節「useful skew」要做的事。


3.3　學術淵源：這不是憑空發明的方法
--------------------------------------------------------------------------------
這套「把延遲限制改寫成圖上的邊，用負環判斷可行性」的技巧，是演算法教科書裡的
標準內容，不是這個專案自己想出來的新方法：

  - 「差分限制系統」（system of difference constraints）轉換成單源最短路徑
    問題，是 Cormen / Leiserson / Rivest / Stein 合著的《Introduction to
    Algorithms》（CLRS）裡，單源最短路徑章節的標準小節主題：系統 x_j − x_i ≤ w_ij
    有解，當且僅當對應的限制圖沒有負環，Bellman-Ford 演算法可以直接找出一組解。

  - 把這套技巧具體套用在「時鐘 skew 排程」上，最常被引用的奠基性論文是
    J. P. Fishburn, "Clock Skew Optimization," IEEE Transactions on Computers,
    vol. 39, no. 7, 1990。這篇論文把 setup/hold 限制表示成一張圖、用類似
    Bellman-Ford 的鬆弛法求解，跟這裡的 psi/box edge/cross edge 設計是同一套
    數學結構。

  - SPFA（Shortest Path Faster Algorithm）是 Bellman-Ford 的佇列最佳化版本
    （只處理「距離剛被更新」的節點，不是每輪暴力鬆弛所有邊），最早由段凡丁於
    1994 年提出，在中文圈的演算法／競賽教學裡是常見的名稱，英文文獻裡通常
    直接稱為 queue-based Bellman-Ford。

  - 用「二分搜尋一個可行性判斷單調的參數」去找最佳閾值（這裡是 tau），是
    演算法設計裡泛稱「binary search on the answer」的通用模式，沒有特定
    單一論文，但是非常標準、廣泛使用的技巧。

（引用時請自行核對卷期頁碼等精確書目資訊，這裡只保證作者/主題/年份/出處正確。）


3.4　可行性檢查：差分限制系統與負環
--------------------------------------------------------------------------------
把所有 box edge + cross edge 丟進同一張圖，這是經典的「差分限制系統」：這個系統
有解，當且僅當圖上沒有「負環」（沿著一圈邊走一輪，權重加總是負的）。用 SPFA
檢查負環，所有節點從 psi=0 出發，只有真的被限制逼著移動的節點才會偏離 0——這
保證找到的是「最小擾動」的解，不是隨便一個可行解。


3.5　二分搜尋找出最佳 tau
--------------------------------------------------------------------------------
    lo = 目前的 WNS（一定可行，因為 psi 全部維持 0 就滿足）
    hi = 先用指數展開法找一個不可行的上界
    重複二分：
        mid = (lo+hi)/2
        若 SPFA 確認 tau=mid 可行 → lo = mid（記住這組 psi）
        否則                      → hi = mid
    直到 hi−lo 小於門檎值，回傳 lo 跟對應的 psi

最後得到「resize-only 情況下，數學上能做到的最佳 WNS」，以及每條 branch 應該
調整到的延遲值（`raw = orig + psi(child) − psi(parent)`，再夾回 [lo, hi] 範圍內）。


3.6　完整數字範例
--------------------------------------------------------------------------------
用一個簡化過的小例子走一遍（其他分支假設先固定不動，只留一條 branch 可調，
方便看清楚機制）：

                    BUF_FORK（固定，delay=0.05）
                   /                          \
                BUF_L（固定，delay=0.02）      BUF_C2 ← 要調的 branch（fanout=1）
                  │                              │
                 FF_A（path P 的 launch）        FF_C（path P 的 capture）

    BUF_C2 目前延遲 0.02，library 允許範圍 [0.01, 0.06]
    clock_period=1.0　t_setup=0.1　data_ss(P)=0.95
    目前 d_clk_ss(A)=0.07　d_clk_ss(C)=0.07　skew_ss=0
    目前 slack_setup_ss(P) = 1.0−0.1−0.95+0 = −0.05　（違規，這就是 3.2 節的 base）

Box edge（BUF_C2 這條 branch，lo=0.01, hi=0.06, orig=0.02）：
    BUF_FORK → BUF_C2，權重 0.04　　　BUF_C2 → BUF_FORK，權重 0.01

Cross edge（path P，setup，base = −0.05）：
    FF_C → FF_A，權重 = −0.05 − tau

（FF_A、FF_C 跟各自 parent 之間是「Insertable」邊，被釘在 psi=0 跟 parent 強制相等；
 BUF_L、BUF_FORK 在這個簡化例子裡假設也固定在 psi=0。）

代入可行性條件：
    psi(FF_A)=0 ≤ psi(FF_C) + (−0.05−tau)
    ⟹ psi(BUF_C2) ≥ 0.05 + tau　　（因為 psi(FF_C)=psi(BUF_C2)）
    同時 box edge 限制：psi(BUF_C2) ≤ 0.04

    要兩者同時滿足：0.05 + tau ≤ 0.04　⟹　tau ≤ −0.01

二分搜尋找到的最佳 tau = −0.01。對應 psi(BUF_C2) = 0.04（卡在上界），換算回真實
延遲：0.02 + 0.04 − 0 = 0.06，正好是 BUF_C2 的上限 d_ss_max。

驗證：新 d_clk_ss(C) = 0.05+0.06 = 0.11，skew_ss = 0.11−0.07 = 0.04，
新 slack = 1.0−0.1−0.95+0.04 = −0.01　✓ 跟 tau 完全吃合。

這個例子裡 WNS 從 −0.05 改善到 −0.01，但沒辦法完全消除違規，因為 BUF_C2 的延遲
範圍只能加到 +0.04，不夠補滿 0.05 的缺口——這就是「resize-only 數學上的極限」，
真實情況裡所有 branch 同時自由、所有 path 同時檢查，SPFA + 二分搜尋是一次性對
整張圖做全域最佳化，不是一條一條輪流調。



================================================================================
第四部分　Phase 0 — 找出該插入 buffer 的位置
================================================================================
→ src/insert_select.cpp, src/pd_mutate.c

4.1　第一次呼叫 LP Init：取得 resize-only 的最佳解
--------------------------------------------------------------------------------
Phase 0 一開始，先呼叫第 3 節的 LP Init 演算法一次，這時候的 Branch 模型完全是
原始設計（還沒有任何插入），算出「假設完全不插入任何 buffer，數學上 resize 最好
能做到多少」。這次呼叫的結果不會被直接套用到 design 上，純粹是拿來當「診斷工具」，
看接下來 4.4 節要怎麼決定插入候選。


4.2　為什麼光靠 resize 不夠：一個具體例子
--------------------------------------------------------------------------------
先回答一個根本問題：什麼情況下，單純換既有 buffer 的 cell 沒辦法解決違規，
非得插入新 buffer 不可？

答案不是「resize 的可調範圍不夠大」，而是「這顆 buffer 同時要服務有衝突需求的對象」。
看下面這個例子：

                    BUF_FORK
                   /         \
                BUF_L        BUF_SHARED   ← fanout=2，FF_C、FF_D 共用
                  │            /     \
                 FF_A        FF_C    FF_D

  - path P：launch=FF_A、capture=FF_C，目前 setup 違規，需要讓 FF_C 的時鐘
            「晚一點到」——也就是要增加 BUF_SHARED 的延遲。
  - 但 FF_D 同時也是某條其他 path 的端點，增加延遲反而會讓那條 path 變差。

resize BUF_SHARED 完全解不開這個衝突：它只有一個延遲值，FF_C 跟 FF_D 被迫共用同一個
數字，沒辦法「對 FF_C 這邊加、對 FF_D 那邊不變」。換成 library 裡任何一顆 cell都沒用，
因為問題不是延遲不夠大，是這個延遲被綁在一個有衝突需求的共享資源上。

解法：在 BUF_SHARED 跟 FF_C 之間插入一顆新 buffer，把 FF_C 這條路徑獨立出來。
BUF_SHARED 維持對 FF_D 最好的值，新插的這顆專門負責 FF_C 需要的延遲調整。
這才是插入操作真正要解決的問題：拆開一段「被迫共享、但需求衝突」的關係。

反過來說：如果 FF_C 的正上方那顆 buffer本來就是獨佔的（只驅動 FF_C 一個，沒有
FF_D 這種共享對象），resize 它就已經有完全的自由度，插入完全沒必要。


4.3　怎麼找插入候選邊：往上爬，找第一個真正分岔的祖先
--------------------------------------------------------------------------------
對每一條目前違規的 path（setup 或 hold 任一違規即算），檢查它的 launch FF 跟
capture FF：

    find_branch_point(FF)：
        child = FF
        cur   = FF 的 parent
        while cur 存在且是 buffer：
            若 cur 驅動超過一個 child（真正的分岔點）：
                回傳 (cur, child)　← 這就是插入候選邊
            否則（cur 是獨佔的，只服務這一個 FF）：
                child = cur
                cur   = cur 的 parent
        回傳「找不到」（一路到 root 都沒有分岔，代表完全沒有要解耦的對象）

這個搜尋的意義：不是固定看 FF 的「直接」parent 是否分岔，是沿著一路往上、跳過
所有「目前已經獨佔、沒有共享衝突」的 buffer，直到碰到第一個真正有共享關係的祖先
為止——因為只有「有共享」的地方，插入才有意義（呼應 4.2 節的結論）。

【一個常見的誤解，先說清楚】
　插入點選在「分岔點正下方」還是「FF 正上方」，其實對結果沒有差別——只要中間這段
　是完全獨佔的鏈，延遲是線性疊加的，新 buffer放在鏈的哪裡，這個 FF 能達到的延遲
　範圍完全相同。往上爬真正的作用，是用來**判斷這個 FF 值不值得插入**（有沒有
　真正的分岔可以解耦），不是為了找一個「更好」的插入位置。


4.4　篩選訊號：用 LP Init 算出的殘餘違規，而不是原始違規
--------------------------------------------------------------------------------
4.3 節「目前違規的 path」，指的不是輸入檔案裡的原始違規，是 4.1 節呼叫 LP Init
之後，*依然*違規的那些 path。理由：很多原始違規光靠 resize 就能解決，那些地方
插 buffer 只是白白增加面積；用 resize-only 跑完之後的殘餘違規當訊號，比用最原始
的違規精準得多。


4.5　Buffer-chain DP 表：怎麼評估插入後的面積　（→ src/lp_buffer_dp.cpp）
--------------------------------------------------------------------------------
4.1 節 LP Init 解出來的延遲是連續數值，還沒對應到任何具體 cell，但 Phase 0 需要
一個「這個延遲大概要花多少面積」的估計，才能評估插入候選的代價。這就是 Buffer-
chain DP 表（`LpBufferChainDp`）要解決的問題：

    「要驅動 fanout 個東西、總延遲剛好是 d，用『零或多顆 fanout=1 小 buffer
      串接、最後接一顆真正驅動 fanout 個東西的大 buffer』這種接法，最少要花
      多少面積？」

建表分兩步：
  1. 先算純串接 fanout=1 buffer 能湊出哪些延遲值、最小面積各是多少
  2. 對每個 fanout n，把第 1 步算出的某段前綴鏈，接上一顆真正驅動 n 個 child
     的最終 buffer，湊出 (n, 總延遲) → 最小面積 的對照表

這張表只在 Phase 0 用到，後面的 Greedy（第 6 節）跟最終套用（第 7 節）都不再
使用它（函式簽名裡仍會收這個參數，但標成未使用）。


4.6　多次找到同一個 FF：去重處理
--------------------------------------------------------------------------------
同一顆 FF 可能同時是好幾條違規 path 的 launch 或 capture（比方說它是 path P1 的
launch、又是 path P2 的 capture）。`find_branch_point` 對同一個 FF 不管被呼叫
幾次，算出來的結果保證一樣（純粹由樹的結構決定，跟是哪條 path 觸發查詢無關），
所有候選邊先丟進一個「集合」（自動去重），最後才真正逐一插入——這樣同一個 FF
被問到幾次，最後也只會在那條邊插入一次。


4.7　Zero Cell 安全閥：讓插入決策可以被撤銷　（→ src/pd_mutate.c）
--------------------------------------------------------------------------------
插入一顆新 buffer，理論上一定要付出至少「最小 cell 面積」的代價，而且没有一個
天然的「事後發現插錯了、撤銷掉」的機制——一旦插入，面積就永久加上去了。

解法：在 cell library 裡（只存在於記憶體中的 design 物件，從來不寫進真實輸出）
多加一顆人工合成的 cell：

    面積 = 0、所有 fanout 下的延遲都是 0、max_fanout = 1
    （max_fanout 設 1 就好：NEW_BUF_X 一定只有單一個 child）

並且透過 2.1 節的 allow_zero_cell 規則嚴格把關：**只有我們自己插入的 NEW_BUF_*
才看得到這個選項，既有的 buffer 永遠看不到**。

效果：
  - LP Init（第 3 節）、Greedy（第 6 節）在評估「這顆插入的 buffer 該設多大」
    的時候，「縮到 0（等於沒插入）」自然成為其中一個合法選項，跟所有真實 cell
    選項一視同仁地被比較、被選擇
  - 一旦某顆插入的 buffer 在最終解裡被選中這顆零成本 cell，代表它對目前的
    timing/area 貢獻恰好是 0，跟「它根本不存在」在數學上完全等價
  - Phase 3（7.2 節）看到這種情況，就把它從樹上物理移除，輸出檔案裡不會出現
    一顆現實中不存在的 cell

這個機制讓插入候選可以放得比較大膽：插錯的地方，搜尋過程會自然把它縮到 0，
最後一步被清掉，不會留下永久的面積稅。

插入完成、安裝好 zero cell 之後，Branch 模型要整個重建（拓樸變了），這個重建
後的模型，才是 4.1 節說的「2.2 節步驟 (d)」，緊接著進入第五部分 Phase 1。



================================================================================
第五部分　Phase 1 — 套用 LP Init 的解
================================================================================
→ src/main.cpp, src/lp_mo_init.cpp

5.1　第二次呼叫 LP Init：同一套演算法，新的 Branch 模型
--------------------------------------------------------------------------------
這裡呼叫的，跟 4.1 節是**完全相同的演算法**（第 3 節），差別只在於這次的
Branch 模型已經是 Phase 0 插入、重建過後的版本——新插入的 NEW_BUF_* 也是正常的
ExistingBuf branch，而且它們的 bounds 因為 allow_zero_cell 而含有 0 這個選項。
LP Init 演算法本身完全不需要知道「這個 branch 是不是插入的」，它只是吃 bounds，
bounds 怎麼算進去 zero cell 的，是第 4.7 節 / 第 2.1 節的事——這正是整個
zero cell 安全閥設計優雅的地方：上層機制改了，下層的精確解演算法一行都不用動。

這次解出來的，才是真正要餵給 Phase 2 Greedy 的起跑點。


5.2　把連續解吸附回真實 cell（消除幽靈 Buffer）
--------------------------------------------------------------------------------
LP Init 解出來的延遲是連續數值，不對應任何真實 cell。套用前要先「吸附」到
library 裡最接近的真實選項：

    對每條 branch b：
        target = LP Init 算出的延遲值
        在 library 所有 cell 裡（若 !allow_zero_cell 則排除 zero cell，
                                  並排除 fanout 超過該 cell 的 max_fanout 的選項）
            找跟 target 差距最小的 cell，指定給這條 branch 的 child 節點
    重新跑真正的 timing engine，算出沒有「LP 內部估計誤差」的真實分數

（4.1 節 Phase 0 的第一次 LP Init 呼叫，並不會做這個吸附動作——那次純粹是用連續
解去評估殘餘違規，不會真的套到 design 上；只有這次 Phase 1 的解才會真正套用。）



================================================================================
第六部分　Phase 2 — Greedy 區域搜尋
================================================================================
→ src/greedy_postlp.cpp

這一步從 Phase 1 的解開始，反覆嘗試「換哪一顆 buffer 的 cell 能讓分數變好」，
是傳統的 coordinate-descent hill-climbing。先講清楚三個層次的詞彙：

    commit（換一次 cell）　⊂　pass（把所有 branch 依序檢查一輪）　⊂　attempt（一次完整收斂）

（這一節只講「演算法概念上在做什麼」；這個迴圈具體怎麼被實作得夠快，獨立整理在
第八部分 8.3、8.4 節。）


6.1　最內層：一次 commit
--------------------------------------------------------------------------------
對某個 branch b，在它所有候選 cell（已經依 bounds 篩選過，含 zero cell 如果
allow_zero_cell 為真）裡，試著換上去、量分數變化、量完馬上換回原狀，找出能讓
分數「嚴格變好」（超過一個極小門檎值）的最佳候選。如果有，就真的換上去（commit）。


6.2　中間層：一次 pass
--------------------------------------------------------------------------------
    pass(order)：
        improved = false
        對 order 裡每一個 branch b（依序）：
            嘗試 6.1 節的 commit
            若真的換了：improved = true
        回傳 improved

注意：同一個 pass 裡，前面的 branch 如果剛換過 cell，後面的 branch看到的就是
「換過之後」的狀態，不是 pass 開始時的舊狀態。


6.3　最外層：一次 attempt（converge）
--------------------------------------------------------------------------------
    converge(order)：
        重複呼叫 pass(order)，直到某一次 pass 回傳 improved=false
        （也就是整整一輪、一個 branch 都沒換）才停下來

這個「整輪都沒人能變好」的狀態，就是這次 attempt（這個起點、這個固定順序）底下，
單靠換單一個 branch 已經到不了更好結果的「局部最優」。

【為什麼這個過程保證會結束，不會卡死】
　每一次 commit 都要求分數「嚴格變好」，所以分數是單調上升的數列；分數有上限、
　候選又是有限離散選項，這個過程不可能無限持續。即使兩個 branch 看起來在互相
　拉扯（改 A 讓 B 變差、改 B 又讓 A 變差），每一輪拉扯仍然讓全域分數淨成長一點，
　最壞情況只是多繞幾輪 pass，最終一定會收斂。


6.4　怎麼決定 attempt 的走訪順序：權重設計
--------------------------------------------------------------------------------
在每一次 attempt 開始之前（也就是還沒做任何 commit 的起點狀態，稱為 start），
算一次每個 branch 的權重：

    weight(b) = 1.0 + Σ severity(p)，對 b 牽涉到的每一條「目前違規」的 path p
    其中 severity(p) = max(0, −slack_setup_ss(p)) + max(0, −slack_hold_ff(p))

用「違規嚴重度」而不是單純「違規 path 的數量」：一個牽涉到一條嚴重違規 path 的
branch，理應比牽涉到三條剛好踩線的 branch 更優先處理——這才對應分數公式真正
在意的東西（TNS/WNS 看的是 slack 大小，不是違規 path 的個數）。這個權重只在
start 這個狀態算一次，整個函式共用。


6.5　第一次 attempt：依權重排序，不隨機
--------------------------------------------------------------------------------
    order = 把所有 branch 依 weight 由大到小排序
    converge(order)
    best = 這次收斂完的結果

固定用「最關鍵的先處理」這個順序，不加隨機。這是因為大型測資常常時間緊繃，
attempt 1 本身就可能吃掉大部分預算，沒有機會跑到後面的隨機嘗試——讓 attempt 1
直接用最有信息量的順序，確保即使只跑得起這一次，也是最好的一次。


6.6　後續 attempt：加權隨機，每次都從同一個起點開始
--------------------------------------------------------------------------------
    迴圈，直到「連續 50 次沒進步」或「時間用完」：
        restore(start)　　　← 永遠從同一個起點重來，不延續上一次的結果
        order = weighted_shuffle(weight)
        converge(order)
        若這次的分數 > best 的分數：best = 這次的結果（耐心重置）
        否則：耐心 −1
    restore(best)

weighted_shuffle 用 Efraimidis–Spirakis 方法：每個 branch 抽一個 0~1 的隨機數
u，算 key = u^(1/weight)，所有 branch 依 key 由大到小排序。權重越高，key 越
容易接近 1，越容易被排到前面——但不是保證，是機率上的偏好。如果所有權重相等，
這個方法會退化成跟均勻隨機排列完全等價，確保「加權」不會破壞掉「多樣化探索」
這個核心機制，只是把均勻分佈換成有偏的分佈。

這個隨機探索迴圈最多只用「attempt 1 跑完後剩餘時間的一半」，另一半故意留給
main.cpp 的 dual-seed 安全網（6.7 節）。


6.7　跟 main.cpp 的雙重保險（dual-seed）
--------------------------------------------------------------------------------
Greedy 是 hill-climbing，從「更好的起點」不保證收斂到「更好的終點」（實測觀察
到的現象）。main.cpp 因此呼叫 greedy_post_lp 兩次：

    第一次：種子 = Phase 1 的解
    第二次：種子 = 完全沒被 Phase 1 動過的原始設計

兩次的結果取分數較高者，當作最終要套用的解——這保證了「換用 Phase 1 當起點」
這個設計，永遠不會比「沒有 Phase 1、直接從原始設計開始」更差。

第七部分　Phase 3 — 套用最終解、清理、輸出
================================================================================
→ src/sa_apply.cpp, src/pd_mutate.c, src/pd_checker.c, src/pd_output.c

7.1　套用最終解
--------------------------------------------------------------------------------
跟 5.2 節相同的「吸附到最近真實 cell」邏輯，套用 Phase 2 贏家的延遲值：

    對每條 ExistingBuf branch：
        在 library 所有合法 cell 裡，找跟目標延遲誤差最小的 cell，指定給
        這條 branch 的 child 節點
    重新跑真正的 timing engine


7.2　移除縮到 0 的插入 buffer
--------------------------------------------------------------------------------
這是 4.7 節 zero cell 安全閥真正發揮作用的地方：

    對 design 裡每一個節點 n：
        若 n 不是 buffer，或 n 目前指定的 cell 不是 zero cell，
           或 n 的名字不符合 NEW_BUF_* 的格式：
            跳過　　← 最後這個名字檢查是防呆：即使真的有 bug 讓既有元件
                       意外被配到 zero cell，也絕對不會去刪除一個既有元件，
                       寧可讓下一節的合法性檢查抓到、整批 fallback
        否則：
            把 n 從樹上斷開：n 的 parent 原本指向 n 的那個 slot，改成直接
            指向 n 唯一的那個 child；n 整個保留在記憶體陣列裡（id 不變），
            但從此沒有任何人的 children 列表指向它

因為 zero cell 本身就是 0 延遲、0 面積，這個移除動作對 timing/area 數學上
不會造成任何變化，純粹是為了不讓輸出檔案出現一顆現實中不存在的 cell（被斷開
的節點，輸出時自然不會被遍歷到，等於從結果裡消失）。


7.3　最終合法性檢查　（→ src/pd_checker.c）
--------------------------------------------------------------------------------
輸入：orig（完全沒被動過的原始設計）、mod（準備要輸出的設計）。

第一步：從 mod 的 root 開始做一次 DFS，標記所有「真正可達」的節點（7.2 節斷開
的孤兒節點不會被標記）——下面所有檢查都只看這個可達集合，孤兒節點完全不參與。

    結構自洽　每個 FF 必須是 sink；每個非 FF 節點必須至少有一個 child；
              每顆 buffer 的 fanout 不能超過它指定 cell 的 max_fanout；
              沒有任何 buffer 留在 zero cell 上；parent/child 雙向指標一致

    命名唯一　所有可達節點的名字不能重複

    既有元件保留　orig 裡每一個元件，名字必須還在 mod 裡找到、kind 不變；
                  mod 裡所有不屬於 orig 的元件，必須是名字符合 NEW_BUF_<n>
                  格式的 buffer

    祖先順序不變　orig 裡任意元件的祖先鏈，在 mod 裡（跳過新插入的 buffer後）
                  必須完全對應，新 buffer 只能「插在邊上」，不能改變任何兩個
                  既有元件原本的祖先/子孫關係

只要任何一項失敗，main() 改成輸出 orig_design 保底——犧牲這筆測資的改善，
但絕不能被判 0 分。


7.4　寫出結果
--------------------------------------------------------------------------------
寫 result.txt（分數報表，含 baseline / Phase 1 / Greedy 後三個階段的數字）跟
modified_clk_tree.structure（真正要交的結果檔，只列出從 root 走得到的節點）。



================================================================================
第八部分　效能與工程優化
================================================================================
這一部分跟前面完全不同性質：第三～七部分講的是「演算法該怎麼算」，這一部分講的
是「怎麼讓它在 600 秒內真的算得完」。這些優化不影響最終答案（同一個演算法、同
一個輸入，優化前後算出來的分數理論上完全一樣），純粹是把原本太慢、會吃光時間
預算的實作方式，換成更快的等價寫法。


8.1　時間預算管理　（→ src/main.cpp 開頭）
--------------------------------------------------------------------------------
比賽硬限制是 600 秒（含讀檔、計算、寫檔）。程式用「倒數時鐘」的方式分配預算：

    wall_t0       = 程式啟動的瞬間（main() 第一行就記錄）
    total_limit   = 600（可被環境變數覆寫，比賽用預設值）
    kTailReserveSec = 15　// 留給 Phase 3 收尾、寫檔的安全邊界
    wall_deadline = wall_t0 + (total_limit − kTailReserveSec)　≈ 585 秒

每一個會花時間的步驟，呼叫前都重新算一次：

    這步驟的預算 = min(這步驟自己的上限, wall_deadline 還剩多少時間)

這樣設計的好處：即使前面的步驟意外拖久了，後面步驟的預算會自動跟著縮短，不會讓
整體執行時間失控。kTailReserveSec 從原本的 5 秒提高到 15 秒，是為了在不確定最終
評分機器的時鐘穩定性的前提下，多留一點緩衝（細節見附錄 B）。


8.2　讀檔效能：O(n²) 名字查詢瓹頸　（→ src/pd_parser.c）
--------------------------------------------------------------------------------
【這重要嗎？非常重要——開發紀錄顯示，修正前這個瓹頸在大測資上浪費了 150~220
秒以上，等於還沒開始任何最佳化計算，600 秒裡就先燒掉了快三分之一到三分之一強。】

先用一個生活化的類比說明問題本身：輸入檔案裡，`SS_delay.rpt`、`FF_delay.rpt`
記錄每一條 path 的 launch/capture 端點時，用的是「節點名字」這種字串（例如
`"FF_1023"`），不是數字編號。如果想知道某個名字對應到哪一個節點，最直覺的做法
是「從頭到尾一個一個比對名字，比對到一樣的就停下來」——這就像在一本沒有按字母
排序、也沒有索引的電話簿裡找一個人，只能從第一頁翻到最後一頁，一個名字一個
名字核對。翻一次電話簿找一個人還可以接受，但如果要「對每一條 path 都重新翻一次
整本電話簿」，總成本就是「電話簿頁數 × path 數量」，兩個數字都很大的話，乘出來
的總量會非常驚人。

具體到這個程式，有兩個地方會發生這種「重複翻電話簿」的情況：

  (a) 每一條 path 的 launch/capture 名字，要對應回 `clk_tree.structure` 解析
      出來的節點編號。逐一比對的成本：單次查詢 O(n_nodes)，n_paths 條 path
      全部做完是 **O(n_nodes × n_paths)**。

  (b) `FF_delay.rpt` 記錄的是跟 `SS_delay.rpt` 同一批 path，但要把每一行的
      hold 延遲，填回 `SS_delay.rpt` 已經建立好的對應 path 上。逐一比對的
      成本：單次查詢 O(n_paths)，全部做完是 **O(n_paths²)**。

在最大的測資（testcase4：約 5.7 萬個節點，path 數量達十萬量級）上，這兩個操作
的總運算量達到 10¹⁰ 量級——這就是為什麼開發紀錄會具體寫下「150~220+ 秒被浪費
掉」這個數字。在 600 秒的總預算裡，少了這 150~220 秒，等於 Phase 2 Greedy
能跑的時間直接少了四分之一到三分之一以上，分數會明顯變差。

解法：讀檔時先建兩張 hash map（「節點名字 → 節點編號」、「launch+capture 組合
鍵 → path 編號」）——這就像幫電話簿加上字母索引，要找一個名字不用整本翻過，
直接跳到對應的索引位置，平均一次查詢只要 O(1)。整個讀檔流程因此從 O(n²) 量級
降到 O(n_nodes + n_paths)。


8.3　Greedy 的增量計算：不必整張圖重算　（→ src/greedy_postlp.cpp）
--------------------------------------------------------------------------------
6.1 節說「試著換上去、量分數變化」，這裡講這個「量分數變化」具體怎麼做到很快。

如果每次想知道「branch b 換成某顆候選 cell 之後分數會變成多少」，都老老實實
重新跑一次完整的 timing engine（重新算過所有 path 的 slack），成本是 O(n_paths)
一次；Greedy 一個 pass 要對每個 branch 試過好幾個候選 cell，總成本會是
O(n_branches × n_candidates × n_paths)——這個量級對大測資來說完全不可行。

關鍵物理觀察：resize 一顆 buffer，只會讓它**整個子樹**的累積延遲一起平移同一個
delta（因為子樹裡每個節點的累積延遲，都是把這顆 buffer的延遲加總進去），所以
一條 path 的 slack 會不會被影響、影響多少，只取決於它的 launch 或 capture 端
是否在這顆 buffer 的子樹底下：

    若 capture 端在子樹下：slack_setup_ss 變化 = +delta（sign = +1）
    若 launch  端在子樹下：slack_setup_ss 變化 = −delta（sign = −1）
    若兩端都在子樹下：兩個方向的變化恰好抵消（sign = 0，這條 path 直接排除）

所以可以針對每個 branch，事先算出一份「受影響的 path 清單，每條附帶 +1/−1 的
符號」（怎麼有效率地建出這份清單，見 8.4 節）。要試一個候選 cell 時：

    1. 算出這顆候選 cell 帶來的 delta_ss / delta_ff
    2. 只更新「受影響清單」裡的那些 path 的 slack（不是全部 n_paths 條）
    3. 用一個 std::multiset 維護所有 path 的 setup slack（取最小值＝WNS 只要
       O(log n)），用一個累加變數維護 TNS（每次只調整變動的那一條，O(1)）
    4. 讀出這次試驗後的分數
    5. 用「相反的 delta」再做一次步驟 2，把剛剛的試驗完全復原

整個「試一個候選、看分數、復原」的成本變成 O(這個 branch 受影響的 path 數量)，
不是 O(n_paths)——對大部分 branch 來說，受影響的 path 數量遠遠小於全部 path
數量。每跑完一個 pass，會用真正的 timing engine 重新算一次完整數值，把這個
反覆試驗/復原過程裡可能累積的浮點數誤差校正回來，避免長時間執行後數值飄掉。


8.4　Greedy 的前置作業：「受影響 path 清單」要怎麼建才夠快
--------------------------------------------------------------------------------
8.3 節提到，每個 branch 需要一份「受影響 path 清單」。這份清單本身要怎麼建立，
也有同樣的效能陷阱。

最直覺的做法：對每個 branch，先找出它的整個子樹（哪些節點在底下），然後**逐一
檢查全部 n_paths 條 path**，看每條 path 的 launch/capture 是否落在這個子樹裡。
檢查「是否落在子樹裡」如果用一個跟節點數一樣大的標記陣列，建這個標記陣列本身
要 O(n_nodes)，外加掃過 n_paths 條 path 是 O(n_paths)，每個 branch 都要重做
一次這兩步，n_branches 個 branch 總共是 **O(n_branches × (n_nodes + n_paths))**
——對 testcase4 這種有數萬個 branch、十幾萬條 path 的測資，這個建表步驟本身
就足以拖垮整個程式。

解法：反過來建索引。不要「對每個 branch 找哪些 path 落在它的子樹」，改成先
**一次性**（O(n_paths)）建出「對每個節點，有哪些 path 把它當 launch、有哪些
path 把它當 capture」的反查表：

    launch_paths[node]  = 所有把 node 當 launch 端的 path 編號
    capture_paths[node] = 所有把 node 當 capture 端的 path 編號

接下來對每個 branch，只需要走訪它的子樹（子樹本身多大就走訪多少節點，不用
碰任何跟這個子樹無關的節點），對子樹裡每一個節點，直接查 launch_paths /
capture_paths（O(1) 平均查詢），不用掃描任何一條跟這個節點無關的 path。
總成本降到「所有 branch 的子樹大小總和」加上建反查表的 O(n_paths)，遠遠小於
原本的 O(n_branches × (n_nodes + n_paths))。

附錄 B　已知的環境風險：計時漂移
================================================================================
在開發過程中的計時稽核發現：在某些虛擬化環境（本機開發用的 WSL2）下，連續高負載
運算超過約 10 分鐘時，程式內部用 `std::chrono::steady_clock` 量到的「經過時間」
會穩定比外部真實時間少報約 9~10%（在另一台真正的 Linux 工作站上測試則完全沒有
這個現象，內部與外部時間幾乎完全吃合）。

原因推測是 guest VM 的單調時鐘，在長時間沒有中斷的高負載運算下，跟 host 的真實
時間產生落差，屬於虛擬化環境常見的現象，不是演算法或計時邏輯本身的問題——任何
clock API 都無法在程式內部偵測或修正這種環境層級的落差。kTailReserveSec 從 5
秒提高到 15 秒，就是為了在不確定最終評分機器是否會出現類似落差的前提下，留一個
不依賴環境穩定性的緩衝。
